# Code Audit 2026-11-27

Workstream 6 of [Launch Hardening 2026-11-27](../05%20Production/Launch%20Hardening%202026-11-27.md). Owner brief: "full game deep dive, check every script, refactor, fix issues", because they're scared the game lags or breaks.

**Method:** `lihfolk:audit` checker over all 516 Luau files in `src/` (165k lines). Then five read-only reviews (match server, lobby server, match client Controllers, match client Util, lobby client + shared) using the `roblox-secure-remotes`, `roblox-datastore-safety`, `roblox-anti-exploit-review` and `roblox-performance-audit` procedures. I read the data and purchase layer myself (PlayerDataService, LockerService, RobuxService, ProgressionService). Every finding below was confirmed by reading the code. Performance items are **static, not measured**.

**Result in one line:** no exploit, no dupe, no data loss and no charge-without-grant. The remote handlers and the save layer are solid. The real problems came from one design fact: in lobby and hosted servers every match (and the range) runs its own *copy* of the match services (a runner script), and that copy shares modules, hook lists, client globals and signals with everything else. When a copy is destroyed, anything it owned dies with it, and anything it left behind leaks. Most P1/P2 fixes below are in that seam.

Checker: 3 errors, 0 warnings, 30 info. The 3 errors (`GlobalQueue` MemoryStore calls) were false positives (inside `tryCall`, which pcalls); I moved their ignore comments to the right line. The 30 info `findfirstchild-chain` items were all dismissed: each is a `:: Type?` cast followed by a nil check, or a template child the code builds itself. Only `ShopDisplays.luau:169-173` and `ShopController.luau:1119` are real (see P3 list). After the fixes: 0 errors.

## What was fine (coverage)
- **Remotes:** every OnServerEvent handler in match and lobby (about 35 remotes) rate-limits, type-checks (NaN/inf rejected via `Validate` or hand checks), checks state (alive, phase, held slot, owned seat, PlayZone) and clears its limiter on leave. There is no `InvokeClient`, no client-supplied damage, price or result. Shots: the server issues seed and counter, checks origin against the head plus a wall check, then checks each hit against the pellet ray, the rewound hitbox, the wall path, allies and duplicates. The owner's movement-authority exception (`Shared/Authority`) is deliberate and was left as is.
- **Data:** PlayerDataService writes every change as one atomic `UpdateAsync` with a txId memory, so there is no in-memory copy to save over newer data. A failed read is never treated as a new player. `PlayerData.newer` refuses saves from a newer build. Receipts: there is exactly one `ProcessReceipt`, the PurchaseId is recorded in the same write as the grant, `PurchaseGranted` is returned only after the write, and the PolicyService gate fails closed. ProgressionService uses a fixed txId per match and player.
- **No** `wait()`, `spawn()`, `delay()`, `_G`, `Humanoid:LoadAnimation`, `--!nonstrict` or deprecated teleport APIs anywhere. Every file is `--!strict`.
- **Dead code:** `LockerController.luau` (~1,480 lines, returns at once while `LOCKER_V3`), `LockerAbilities`, `OnbHighlight`, `Panels`, `Menu`, `Icons` (lobby client) are only reached from each other. They were left in place: removing them is cleanup, not a bug fix.

## Explained, not fixed (unowned)
- **`CharacterService.luau:390` verifyBody before prepare (P2).** A late spawn can't be hit for up to about 4 s, because `HitboxHistory.track` runs after `verifyBody`. Running `prepare` first is wrong: the description re-apply rebuilds body parts, so hitboxes would track the old ones. A safe fix needs the re-apply to re-track, measured in Studio. **Follow-up.**
- **`TaskService` Range flush (P3).** A retry uses a fresh txId. It double-counts only if the write landed *and* both the call and the follow-up `readFresh` (4 tries each) failed. Fixing it needs a two-batch queue. Parked.
- **`Damage.hurt` cross-match (P3).** A bot victim isn't checked against the attacker's MatchId. Arenas are 800 studs apart and the range check is 1000, so only line of sight protects them. I didn't change it because range dummies carry their own MatchId rules. Parked.
- **`ModRecall` single `serverHook` slot (P3, latent):** two kits interleaving require and start can swap hooks. **`MatchEndService` resend (P3):** a repeated Leave re-teleports, at most 4/s. **`MapGlass` shatter (P3):** goes to all clients; cosmetic only. **`Motion`/`StatusService` per-player Heartbeat (P3):** profile first.
- **`QueueService` pair-waiting ghost entry (P2):** obsolete. The onboarding session removed that path (`905e96b9`).
- **`Launcher` watchdog requeue after a slow successful teleport (P3)**, **`GlobalQueue` reads the oldest 200 keys (P3)**, **Admin allowlist in ReplicatedStorage (info):** parked in Bugs & Ideas.
- **`ModFeelController.stepCharacters` (P2 perf):** it steps every player with no scope filter. Filtering by scope wouldn't lower the lobby cost (all lobby players share a scope), and could replay stale dash/updraft effects when someone comes back into scope. Needs a measured pass.
- **Client P3 perf list** (static, not measured, owners can take them in a perf pass): DashGhost clones about 250 parts/s per dasher; GripController runs `GetDescendants` per frame while a gun is hidden; ModHud and Viewmodel allocate per frame; StatusTray and BottomHud rewrite unchanged properties every frame; `NumberSequence.new` per frame in RiftforgeEffects and KnifeSwipeFx; MapLife makes a closure per gull per frame; BlastFx builds new RaycastParams per arc jump; LobbyGunDisplays pivots every frame; PadDuelController polls `GetTagged` every 0.1 s; CaseShow has no cap on concurrent onlooker openings; Locker POWERS rebuilds the grid on every change.
